# Online multiplayer, rollback, and prediction

1. Use `@typeonce/ritmo-netcode`: a session per peer owns the input timeline, the checkpoint history, pacing, resyncs, and checksum comparisons. Do not hand-roll a rollback loop with `runtime.checkpoint` and `runtime.rewind`.
2. Pick the model. `Netcode.rollback` for real-time play: input feels immediate, and the simulation must be rewindable (no `local` state; services are sources, plain data, or `Checkpoint.rewindable`). `Netcode.lockstep` for turn-based or slow-paced play: nothing runs twice, every tick waits on the slowest message; give it an `inputDelay` near half the round trip, in ticks. Client prediction against a server is rollback with the server as seat 0.
3. Make the simulation one schedule every peer ticks the same way: fixed step (`Clock`), randomness in a resource (`Random`), math from `Ops`. Nothing in it may depend on the host: the lint rules enforce this.
   - A library that keeps its own world (physics, navigation) is a `Checkpoint.rewindable(value, { save, restore })` service: each checkpoint saves it, each rollback restores it, and systems read `services.<name>.current` every run (never keep it). Mirror what gameplay reads (positions, contacts) into components each tick: the checksum and saves see only the world, and a resync restores the world but not the library, so rebuild the library from those components after one.
4. Input: one `Netcode.seats(schema, { count, idle })`, its `source` provided as the service, captured once at the start of the simulation (`InputCapture.system`). Feed input that holds state (held, aimed at), not one-frame edges: a stalled frame drops its input. Never send remote input with `runtime.send`.
5. Seat 0 hosts. Only seat 0 needs to set up the world before the match: every peer restores its save at the first tick, and again on every resync. Systems outside the simulation that cache entities must tolerate a restore.
6. Drive each peer with `FixedLoop.start({ rate: session.rate, update: session.update({ input, onHalted }) })`. Log every halt in `onHalted`: a `Desynced` is a determinism bug to fix, not noise. `onFailure` is the session ending (a peer left, versions differ).
7. Input delay: for play over the internet give `adaptiveDelay: { min, max }` (for example `{ min: 1, max: 4 }`, a wider `max` for lockstep) rather than guessing a fixed `inputDelay`; the session follows the round trip, and `status().inputDelay` shows the value in use. Keep a fixed `inputDelay` for a known link (LAN, local tests). Give every peer the same `inputDelay` or the same `adaptiveDelay.max`.
8. Effects (sound, particles, a message to a server) come from events the simulation emits, read by host code through `session.events(Event)` (one reader per place that acts on them): play what must happen once from `confirmed()`, start what must feel immediate from `predicted()` and cancel it on `withdrawn()`, and check `lost()`. Never de-duplicate events by tick by hand, and never act on events from a system outside the simulation: ticks rolled back publish their events again.
9. Browser builds pass `hidden: { visibility: BrowserVisibility.make(document), afterMS, then }` (`"stall"` or `"resync-on-return"`) to the session, and the HUD renders `status().hidden` (who everyone is waiting for). Without it, a hidden tab goes silent and the match ends after `timeoutMS`. Test it headless with `MemoryVisibility.make()`: `hide()`, stop calling that peer's `advance`, `show()`.
10. Transport: `WebSocketNetworkLink.make(socket)` through a relay, `WebRtcNetworkLink.make(channel)` between peers (unordered, no retransmits), or implement `NetworkLink`'s three methods over the game's own. Connecting, signaling, and reconnecting stay in the game.
11. Check the match plays the same in every browser before shipping it: record a replay of a scripted match (`Replay.recorder`), commit it with the script that records it, and run `ritmo-devtools verify <entry> <replay> --engines node,chromium,webkit,firefox` in CI (`<entry>` exports `replayTarget`). A `Diverged` engine names the tick and the value: it is a desync waiting to happen between players on those browsers.
12. Before shipping a rollback game, add a test that runs `Netcode.syncTest(runtime, { simulate, seats, rewind: maxRollback })` over a scripted or recorded input: it rewinds after every tick and fails with `RewindDiffers` at the tick whose world comes out different. A module variable, a service that remembers, or a cache outside the world is the usual cause; move it into a resource or component.
13. Debug a desync headless: rebuild it over `MemoryNetworkLink.make({ peers, hostClock: HostClock.test(), seed, latencyMS, jitterMS, loss })` (`link.setLatency(ms)` to change a peer's latency mid-match) with `keepSnapshots: true`, and print `Desync.compare(mine.snapshot, theirs.snapshot)` (`@typeonce/ritmo-devtools`) to see what went apart first.

**Done when** a sync test passes over the game's scripted input, a headless test plays every seat over `MemoryNetworkLink` with latency, jitter, and loss, seeded, rolls back (`status().rollbacks > 0` for rollback), ends with every peer's `runtime.checksum()` equal to one runtime ticked with the inputs the sessions recorded (`Advanced.input`), and keeps `status().verified` climbing through a `resync()`.
