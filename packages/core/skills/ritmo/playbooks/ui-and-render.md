# UI, readouts, and rendering

**Goal:** what is drawn reads the world as plain view data through one projection, and could be replaced without touching the simulation.

**Principles:** the simulation is the game; intents in, plain data out; each piece of state has an owner and a lifetime.

1. Find the projection: the one place the world is read into view data (an inspector run with `runtime.inspect(...)`, or a system writing a transient resource). Add the new fields there; if the game has none, add one instead of reading queries from UI code.
2. Give each UI piece a narrow view model and intent callbacks, not the runtime or a whole host object. Player actions go back as intents ([`mechanic.md`](mechanic.md), step 3).
3. Mirror entities into a renderer through `@typeonce/ritmo-render` (its README); the simulation names no renderer type. A part that is an entity and moves with another is a child entity in a hierarchy, composed by the renderer, never a node attached by hand or a world position computed for drawing. A part that is not an entity (a procedural limb, a trail) is render state (step 4): computed from view data each frame, never written back.
4. Render-only state (animation timers, effects, camera easing) stays in render code, a transient resource, or a system's `local`, with a decision for what it does when a save loads (a load puts a transient resource back to the value the runtime was made with). Cosmetic randomness (shake, particles) draws from its own `Random.make` stream, never the world's random resource: a render system that writes that resource changes the simulation and breaks replays.
5. When the game is pixel art, the camera, scaling, parallax, and text follow the `ritmo-pixel-art` skill's One grid principles: fractions stay in the simulation and are rounded at the draw, the art is scaled by a whole number, and pixel fonts render at whole multiples.
6. Lint the import direction: the simulation imports no UI or render code, and each host folder gets a `no-restricted-imports` rule whose message says where the code belongs.
7. Build each DOM control (a button, a toggle, a slider) once and update its text and attributes in place; never rewrite a region that holds one (`innerHTML`, `replaceChildren`): the rewrite deletes the focused control and drops focus to `<body>`. Give every control a name a test can find it by: its text, or `aria-label` on an icon.
8. A menu that stops play is a modal: `showModal()` on a `<dialog>`, which moves focus in, keeps it there, and makes the page behind inert; an element with `aria-modal="true"` must do all three itself. The menu's own keys (arrows, letters) listen on that element. Handle a `<dialog>`'s `cancel` and `close` events as intents and show it again from the game's state, because the browser closes a dialog on a repeated Escape even when `cancel` is prevented. A splash or wipe that must cover a menu is a `popover="manual"` shown after it, never a `z-index`; a layer the player presses (a crash panel) is its own modal dialog, since everything outside the newest modal is inert.

**Check:** the simulation's headless tests pass unchanged, and the game's check passes. When the page has DOM controls, `ritmo-devtools keyboard` passes with a route through every screen that shows them, and `ritmo-devtools layout` passes on the same route at every screen size the game targets, with its screenshots looked at (the `@typeonce/ritmo-devtools` README).
