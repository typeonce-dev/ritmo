Your game reads "dash" and "move", never a key code. The keyboard, a
gamepad, and a phone screen all produce those same actions, and the player
can switch between them mid-run.

<Game id="controls" />

Walk with the keys, then pick up a gamepad, then open the page on a phone.
The prompts in the corner follow whatever you touched last.

## What you get

- One set of actions for every device. Systems read the actions and never
  ask which device produced them.
- Prompts that follow the player: the input names the device used last and
  whether it has each action.
- A device that cannot do an action has to say so. Forget it and the merge
  does not compile.
- Gamepads, keyboards, and touch screens handled the way players expect:
  dead zones, lost focus, unplugged pads, floating thumb sticks.
- The same input in tests, replays, and the fuzzer, with no browser.

Most web game libraries stop at the raw devices: key codes, and an array of
pad buttons you poll yourself. Turning those into actions, merging them,
and keeping the prompts right is left to you. Ritmo ships that layer.

## Actions, not keys

Declare what the player can do once. Each device binds those actions, and
the merge is the one input your game reads.

```ts twoslash title="input.ts"
import { Controls, Gamepad, Keyboard, Pointer, Touch } from "@typeonce/ritmo-browser"
declare const keyboard: Keyboard.Actions<typeof keys>
declare const mouse: Pointer.Actions<typeof clicks>
declare const gamepad: Gamepad.Actions<typeof pad>
declare const touch: Touch.Actions<"dash", "move">
// ---cut---
const Actions = Controls.actions({
  buttons: ["dash", "pause"],
  vectors: ["move"]
})

const keys = {
  move: Keyboard.vector({ up: ["w"], down: ["s"], left: ["a"], right: ["d"] }),
  dash: [" "],
  pause: ["Escape"]
} as const

const clicks = { dash: ["primary"] } as const

const pad = {
  move: Gamepad.vector({
    stick: "left",
    up: ["dpadUp"],
    down: ["dpadDown"],
    left: ["dpadLeft"],
    right: ["dpadRight"]
  }),
  dash: ["south"], // A on Xbox, Cross on PlayStation, B on Nintendo
  pause: ["start"]
} as const

const controls = Actions.merge({
  // Used together, so they count as one device
  desktop: Actions.group({ keyboard, mouse }), // [!code highlight]
  gamepad,

  // The touch layout has no pause button, and says so
  touch: Actions.lacking(touch, ["pause"]) // [!code highlight]
})
```

A system reads `dash` and `move`. Which key, button, or finger produced
them is not its concern:

```ts twoslash title="move.ts"
import { Controls, Gamepad, Keyboard, Pointer, Touch } from "@typeonce/ritmo-browser"
const Actions = Controls.actions({ buttons: ["dash", "pause"], vectors: ["move"] })
const keys = { move: Keyboard.vector({ up: ["w"], down: ["s"], left: ["a"], right: ["d"] }), dash: [" "], pause: ["Escape"] } as const
const clicks = { dash: ["primary"] } as const
const pad = { move: Gamepad.vector({ stick: "left" }), dash: ["south"], pause: ["start"] } as const
declare const keyboard: Keyboard.Actions<typeof keys>
declare const mouse: Pointer.Actions<typeof clicks>
declare const gamepad: Gamepad.Actions<typeof pad>
declare const touch: Touch.Actions<"dash", "move">
const controls = Actions.merge({ desktop: Actions.group({ keyboard, mouse }), gamepad, touch: Actions.lacking(touch, ["pause"]) })
declare const dash: () => void
declare const walk: (direction: { x: number; y: number }) => void
declare const input: ReturnType<typeof controls.snapshot>
// ---cut---
// In a system: input = resources.input.get(), captured once per update

// Keys, d-pad, stick, or touch stick: never longer than 1, even all at once
walk(input.vectors.move)

if (input.actions.dash.pressed) {
  dash()
}
```

## Prompts that follow the player

`lastUsed` names the device the player touched last, and `available` says
whether it has each action. That is all a prompt needs.

```ts twoslash title="prompt.ts"
import { Controls, Gamepad, Keyboard, Pointer, Touch } from "@typeonce/ritmo-browser"
const Actions = Controls.actions({ buttons: ["dash", "pause"], vectors: ["move"] })
const keys = { move: Keyboard.vector({ up: ["w"], down: ["s"], left: ["a"], right: ["d"] }), dash: [" "], pause: ["Escape"] } as const
const clicks = { dash: ["primary"] } as const
const pad = { move: Gamepad.vector({ stick: "left" }), dash: ["south"], pause: ["start"] } as const
declare const keyboard: Keyboard.Actions<typeof keys>
declare const mouse: Pointer.Actions<typeof clicks>
declare const gamepad: Gamepad.Actions<typeof pad>
declare const touch: Touch.Actions<"dash", "move">
const controls = Actions.merge({ desktop: Actions.group({ keyboard, mouse }), gamepad, touch: Actions.lacking(touch, ["pause"]) })
declare const input: ReturnType<typeof controls.snapshot>
// ---cut---
// "desktop" | "gamepad" | "touch" | null
const device = input.lastUsed

const prompt =
  device === "gamepad" ? "Ⓐ to dash"
  : device === "touch" ? "Tap to dash"
  : "Space to dash"

// false while playing on touch
const showPause = input.available.pause
```

The pad reports its maker too (`devices.gamepad.id`), so the demo above
shows ✕ instead of Ⓐ on a PlayStation pad.

## A missing button does not compile

Every device binds every action, or says which ones it cannot. Leave out
the touch screen's missing pause button and the merge is an error that
names it:

```ts twoslash title="input.ts"
import { Controls, Gamepad, Keyboard, Touch } from "@typeonce/ritmo-browser"
const Actions = Controls.actions({ buttons: ["dash", "pause"], vectors: ["move"] })
const keys = { move: Keyboard.vector({ up: ["w"], down: ["s"], left: ["a"], right: ["d"] }), dash: [" "], pause: ["Escape"] } as const
declare const keyboard: Keyboard.Actions<typeof keys>
declare const touch: Touch.Actions<"dash", "move">
// ---cut---
// @errors: 2322
const controls = Actions.merge({ keyboard, touch })
```

## Replays and the fuzzer play it too

The game declares its input service as the merge's snapshot only, with
`InputCapture.SourceOf`. Any source that produces that snapshot can stand
in for the live devices.

```ts twoslash title="input.ts"
import { Controls, Gamepad, Keyboard, Pointer, Touch } from "@typeonce/ritmo-browser"
const Actions = Controls.actions({ buttons: ["dash", "pause"], vectors: ["move"] })
const keys = { move: Keyboard.vector({ up: ["w"], down: ["s"], left: ["a"], right: ["d"] }), dash: [" "], pause: ["Escape"] } as const
const clicks = { dash: ["primary"] } as const
const pad = { move: Gamepad.vector({ stick: "left" }), dash: ["south"], pause: ["start"] } as const
declare const keyboard: Keyboard.Actions<typeof keys>
declare const mouse: Pointer.Actions<typeof clicks>
declare const gamepad: Gamepad.Actions<typeof pad>
declare const touch: Touch.Actions<"dash", "move">
const controls = Actions.merge({ desktop: Actions.group({ keyboard, mouse }), gamepad, touch: Actions.lacking(touch, ["pause"]) })
// ---cut---
import { Descriptor } from "@typeonce/ritmo"
import { InputCapture } from "@typeonce/ritmo-browser"

// Only the snapshot, not the devices behind it
const ControlsInput = Descriptor.Service<
  InputCapture.SourceOf<typeof controls> // [!code highlight]
>()("Game/Controls")

// In the page: the live merge
// In a test:   the same merge over scripted devices
// In a replay: the recorded snapshots
// In the fuzz: random input a real merge could report
```

Every device has a scripted twin that plays a timeline, so a test presses
"dash" on frame 12 without a keyboard.

A replay records actions, not keys,
so it plays back the same whatever the player had bound. The fuzzer draws
every state a button or stick can report: taps, holds, diagonals. See [Replays that become tests](/features/replays/) and
[Bugs found before players](/features/bugs/).

## What the devices take care of

- **Gamepads.** The browser has no button events for pads, so they are read
  every frame. Taps shorter than a frame still count, sticks get a round
  dead zone, the pad used last is the one followed, and a pad that
  disconnects lets go of everything it held. Buttons are named by place, so
  one binding fits every maker's pad.
- **Keyboard and mouse.** Bound keys do not scroll the page, keys are
  released when the window loses focus, and a key released after a
  modifier changed its character still lets go. Clicks get edges, pointer
  capture, and no context menu.
- **Touch.** Floating sticks that appear under the thumb, each named by the
  vector it drives, so a twin-stick shooter moves with a `move` stick on the
  left and aims with an `aim` stick on the right, both thumbs at once.
  Buttons aim by dragging (tap to use, drag to aim, release to fire), an
  optional swipe area looks around, and the layout is recomputed from the
  screen's size.
