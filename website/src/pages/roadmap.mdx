Ritmo runs the simulation of a game that coding agents write. It is not a
game engine: drawing, sound, saving, servers, and platform SDKs stay in the
game, which plugs them in through typed contracts.

This page lists what Ritmo has added, what it decided not to add, and what
it is waiting on.

## The test for an addition

An addition has to pass one test: **it is only right when it is built into
the runtime.** Access declarations, per-reader streams, the fixed step,
rollback, or the devtools trace have to know about it.

A piece a game can get from an existing library is a playbook in the
[skill](/docs/with-an-agent/), not a package. A piece that is gameplay
stays in the game.

`ritmo-math` is the one exception. It holds the 2D helpers most games
would otherwise rewrite, built on `Ops` so they replay the same on every
engine. A helper gets in when at least two games hand-roll it. Determinism
alone is never the reason: `Ops` and `oxlint --fix` already make any game
math exact.

Every addition keeps the library's rules: wrong code does not compile, a
failure that depends on runtime state is a typed `Result`, and there is one
way to do each thing.

## Shipped

**Bugs found before players.** The [fuzzer](/features/bugs/) plays the game
with seeded input and shrinks each failure to a replay that is already a
test ([#95](https://github.com/typeonce-dev/ritmo/pull/95)). It plays online
matches too, with latency and packet loss, and a sync test checks every
rollback on the tick it happens ([#99](https://github.com/typeonce-dev/ritmo/pull/99)).
Browser games are fuzzed through the same controls the page reads
([#98](https://github.com/typeonce-dev/ritmo/pull/98)).

**Same game in every browser.** `ritmo-devtools verify` plays a recorded
match in Node, Chromium, WebKit, and Firefox and names the first tick they
disagree on ([#101](https://github.com/typeonce-dev/ritmo/pull/101)).
`ritmo-devtools scan` finds inexact math inside the libraries a game brings,
and `oxlint --fix` rewrites the game's own
([#111](https://github.com/typeonce-dev/ritmo/pull/111)).

**Online play that holds up.** Sounds and effects fire once under rollback,
with predictions withdrawn when a rollback undoes them
([#100](https://github.com/typeonce-dev/ritmo/pull/100)). A hidden tab tells
the others instead of freezing the match
([#102](https://github.com/typeonce-dev/ritmo/pull/102)). Input delay follows
the connection ([#106](https://github.com/typeonce-dev/ritmo/pull/106)), and a
physics engine with its own world rolls back with the game
([#97](https://github.com/typeonce-dev/ritmo/pull/97)).

**Debugging an agent can read.** Entities print with names
([#96](https://github.com/typeonce-dev/ritmo/pull/96)), a frame can be stepped
one system at a time ([#108](https://github.com/typeonce-dev/ritmo/pull/108)),
and `why` follows a wrong value back through the systems that produced it
([#103](https://github.com/typeonce-dev/ritmo/pull/103)). Debugging is
headless: the in-page monitor is gone
([#104](https://github.com/typeonce-dev/ritmo/pull/104)).

**Fewer ways to get it wrong.** Timers count steps, and a float timer is a
lint error ([#94](https://github.com/typeonce-dev/ritmo/pull/94)). A link to
a despawned entity is reported to the systems that held it
([#107](https://github.com/typeonce-dev/ritmo/pull/107)). Values can declare
a unit and a range ([#105](https://github.com/typeonce-dev/ritmo/pull/105)),
and a cast to a branded type is a lint error
([#111](https://github.com/typeonce-dev/ritmo/pull/111)).

**A smaller core of math.** `Ops` and `Random` moved into the core.
`ritmo-math` lost the types a game's schema already validates and gained
the helpers every game rewrites: angle wrapping and turning, headings to
vectors and back, frame-rate-independent easing, and circle overlap
([#111](https://github.com/typeonce-dev/ritmo/pull/111)). Child entities'
nodes attach under their parent's in the renderer
([#109](https://github.com/typeonce-dev/ritmo/pull/109)).

## Left to the game, on purpose

These came up in the survey behind this page and were set aside. Each is a
real need; none needs the runtime to be done right.

- **Saving, servers, lobbies, relays.** `runtime.snapshot()` is the save; where
  it goes is the game's. Netcode works over any `NetworkLink`; who connects
  whom is the game's.
- **Audio, haptics, analytics.** Host code that acts on confirmed events.
- **Platform SDKs** (web portals, Discord, Steam, mobile shells). Services the
  game provides, like any other.
- **Renderer adapters beyond Pixi.** A `NodeRegistry` for Three.js is a few
  lines; the skill will show them.
- **Physics engines, pathfinding, geometry, noise, curves, grids.** Libraries
  the game brings. The rewindable service contract above is the one hook
  they need from Ritmo, and `ritmo-devtools scan` says whether one calls
  math that differs across engines (then the game vendors it and runs
  `oxlint --fix`). `ritmo-math` keeps to the 2D helpers most games rewrite;
  it does not port a library's algorithms.
- **Gameplay bundles** (stats, status effects, inventory, dialogue, cameras,
  spawners). Systems the agent writes, with playbooks for the common shapes.
- **Observers and lifecycle hooks, system sets with automatic ordering.** Each
  is a second way to do something the schedule and per-reader streams
  already do explicitly.
- **Faster storage at the cost of types.** Storage is already paged typed
  arrays for numbers behind typed cells. No raw store access will be exposed.
- **An MCP server, hot reload of systems.** Agents drive a `Session` from a
  script today; a system swapped under a running world has no owner for its
  state.

Several of these become playbooks in the skill instead: scene data spawned
into an `EntityScope`, templates as spawn drafts, menu and gameplay input
contexts from `Controls` and run conditions, separate `Random` resources per
subsystem, a camera that follows, and saves over snapshots.

## Next

Recorded, and waiting for a reason:

- **A name for `ritmo-math`.** It now holds 2D helpers only; whether it
  becomes `ritmo-2d` is open.
- **Rewriting `Math.` in named dependencies at build time.** A Vite
  transform, only if vendoring proves painful again and again. It would
  replace vendoring as the one way, never sit beside it.
- **A relation edge-change filter for `RenderSync` hierarchies.** Waits for
  a measured regression.

Rejected: patching the global `Math` at runtime (global, depends on import
order, and misses WebAssembly), and a compile-time ban of `Math.sin` and
the like (TypeScript cannot narrow a global per file).

## How this page was made

A survey of what ECS runtimes, engines, physics and netcode libraries, and
devtools offer (Bevy, flecs, Unity DOTS, bitECS, Koota, Rapier, Box2D, GGRS,
Lightyear, Phaser, Godot, and others), filtered through two independent
scope reviews against the rules above. Open an
[issue](https://github.com/typeonce-dev/ritmo/issues) to argue for an item,
or against one.
